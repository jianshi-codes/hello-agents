# 第一章习题参考答案

> 以下答案不是唯一标准答案，重点是帮助你建立对智能体概念、分类、工程取舍和系统评估的理解。

## 1. 四个 case 是否属于智能体

### case A：一台符合冯·诺依曼结构的超级计算机

单独一台超级计算机不算智能体。

它只是计算资源，本身没有明确目标、传感器、执行器和自主决策循环。只有当它运行某个能够感知环境、独立决策并采取行动的程序时，那个“程序 + 计算平台 + 环境接口”的整体才可以被称为智能体。

### case B：特斯拉自动驾驶系统

属于智能体。

它通过摄像头、雷达、传感器等感知道路环境，通过刹车、转向、加速等执行器影响环境，并且需要根据目标和安全约束做实时决策。

从分类角度看，它可以被理解为：

- 模型式智能体：需要维护车辆、道路、障碍物和周边交通参与者的状态估计。
- 反应式智能体：遇到障碍物时需要毫秒级响应。
- 混合式智能体：既有紧急避障这样的快速反应，也有导航、车道选择等规划行为。

### case C：AlphaGo

属于智能体。

AlphaGo 能感知棋盘状态，评估当前局面，并选择下一步落子行动。它的目标是最大化获胜概率。

从分类角度看，它可以被理解为：

- 规划式智能体：通过搜索评估未来多步局面。
- 目标型或效用型智能体：目标是赢棋，效用可以表现为局面胜率或价值评估。
- 学习型智能体：通过大量棋谱和自我对弈学习策略。

### case D：ChatGPT 扮演的智能客服

如果它只是单轮聊天，不调用任何外部系统，只能算对话模型应用；如果它能够查询订单、读取售后政策、调用退款或工单系统，并基于观察结果持续推进任务，就可以算 LLM Agent。

从分类角度看，它可以被理解为：

- 目标型智能体：目标是解决用户投诉。
- 混合式智能体：既要理解用户情绪并即时回应，也要规划查询、判断和解决流程。
- 工具增强型 LLM Agent：通过外部工具补充订单、物流、售后状态等实时信息。

## 2. 智能健身教练的 PEAS 分析

### Performance

性能度量可以包括：

- 用户健身目标达成度，例如减脂、增肌、提升耐力。
- 训练安全性，例如是否避免心率过高、动作受伤风险。
- 动作标准程度。
- 用户坚持率和满意度。
- 训练计划调整是否合理。
- 饮食建议是否匹配用户目标和身体状态。

### Environment

环境包括：

- 用户身体状态。
- 可穿戴设备数据。
- 健身房或家庭训练空间。
- 训练器械。
- 用户作息、睡眠和饮食记录。
- 历史训练数据。
- 外部因素，例如天气、工作压力、身体疲劳等。

### Actuators

执行器包括：

- App 页面提示。
- 实时语音指导。
- 训练计划调整。
- 动作纠正提醒。
- 强度降低或提高建议。
- 饮食建议。
- 异常心率或高风险动作下的停止提醒。

### Sensors

传感器包括：

- 心率传感器。
- 运动强度和步频数据。
- IMU 姿态数据。
- 摄像头动作识别。
- 用户主动反馈。
- 体重、体脂、睡眠和饮食记录。

### 环境特性

这个任务环境通常是部分可观察的。系统无法完全知道用户真实疲劳程度、疼痛感、心理压力和动作细节。

它也是随机性的。同样的训练计划对不同用户、不同状态下的同一用户，效果都可能不同。

它是动态的。用户心率、体能、疲劳和动作质量会在训练过程中实时变化。

它是序贯的。今天的训练强度会影响明天的恢复和表现。

它也具有连续性。心率、动作角度、速度、训练负荷等数据通常不是离散选项，而是连续变量。

## 3. Workflow 与 Agent 处理退款申请

### 方案 A：Workflow

优点：

- 规则稳定，结果可预测。
- 容易审计和解释。
- 工程实现简单，成本低。
- 适合合规、财务、风控等高约束场景。

缺点：

- 规则僵硬，难处理复杂上下文。
- 对边界情况不够灵活。
- 规则越多，维护成本越高。
- 难以理解用户投诉文本、商品瑕疵证据和历史行为的复杂组合。

### 方案 B：Agent

优点：

- 能理解自然语言投诉和复杂上下文。
- 可以结合订单、物流、用户历史、商品状态进行综合判断。
- 对非标准案例更灵活。
- 可以生成面向用户的解释和安抚话术。

缺点：

- 结果可能不稳定。
- 可能产生幻觉或错误判断。
- 审计和合规难度更高。
- 如果直接给它退款权限，风险较大。

### 适用场景

Workflow 更适合规则清晰、风险高、需要强审计的场景，例如低金额自动退款、高金额审批、特殊商品禁止自动退款。

Agent 更适合处理复杂、非结构化、需要理解上下文的场景，例如用户长文本投诉、商品质量争议、老用户特殊照顾、客服辅助决策。

### 方案 C：混合方案

更合理的做法是采用 Workflow + Agent 的混合方案。

Workflow 负责硬规则和权限边界，例如金额阈值、时间限制、特殊商品限制、人工审批条件。Agent 负责理解用户投诉、总结证据、查询上下文、给出建议和生成回复。

例如：

- 明确符合低风险规则的申请自动通过。
- 明确违反硬规则的申请自动拒绝或转人工。
- 复杂争议案例由 Agent 汇总理由和建议，再交给客服或主管确认。

这样可以同时保留 Workflow 的稳定性和 Agent 的灵活性。

## 4. 为旅行助手添加功能

### 添加记忆功能

可以在 Agent Loop 中增加一个 `memory` 状态，用来保存用户偏好，例如：

- 喜欢历史文化景点。
- 预算范围。
- 不喜欢排队。
- 偏好室内或户外活动。
- 是否带老人、小孩同行。

每轮对话结束后，可以从用户输入和最终选择中抽取偏好并写入记忆。下一轮调用 LLM 时，把这部分记忆加入 prompt。

示例：

```text
Memory:
- 用户喜欢历史文化类景点
- 用户预算不超过 300 元
- 用户不喜欢长时间排队
```

### 门票售罄时自动推荐备选方案

可以新增工具：

```python
check_ticket(attraction: str) -> str
search_alternative(city: str, preference: str) -> str
```

当 `check_ticket` 返回“售罄”时，不直接结束任务，而是把这个结果作为 Observation 反馈给 LLM，让它进入下一轮 Thought，并调用 `search_alternative` 推荐备选景点。

### 用户连续拒绝 3 个推荐后反思

可以维护两个状态：

```python
rejection_count = 0
rejection_reasons = []
```

每次用户拒绝推荐时，记录原因。当 `rejection_count >= 3` 时，强制触发一个 Reflection 步骤，让智能体总结失败原因并调整策略。

例如：

```text
Reflection:
用户连续拒绝了 3 个推荐，原因分别是太远、太贵、不感兴趣。
下一轮推荐应优先选择近距离、低预算、历史文化类景点。
```

本质上，这是在 `Thought-Action-Observation` 循环中加入长期状态和自我反思能力。

## 5. 系统 1 与系统 2 的智能体应用示例

以金融风控智能体为例。

### 系统 1 负责的任务

系统 1 适合处理快速、直觉式、模式识别类任务，例如：

- 检测异常交易金额。
- 识别陌生设备登录。
- 判断登录地点是否异常。
- 发现短时间高频交易。
- 根据历史行为快速生成风险分数。

这类任务需要低延迟，适合用规则模型、机器学习模型或深度学习模型快速判断。

### 系统 2 负责的任务

系统 2 适合处理慢速、审慎、可解释的推理任务，例如：

- 综合用户历史、商户类型、交易时间、设备指纹进行多因素判断。
- 分析是否存在盗刷、洗钱或账户接管风险。
- 根据风控政策决定放行、拦截、二次验证或人工复核。
- 生成可审计的风险判断理由。

### 两者如何协同

系统 1 先对所有交易进行实时初筛。低风险交易直接放行，高风险或不确定交易交给系统 2 深度分析。

系统 2 结合规则、知识库、图谱关系和历史上下文进行推理，输出最终决策和解释。系统 2 发现的新型风险模式，也可以反过来沉淀为系统 1 的新特征或新规则。

这种协同方式兼顾了实时性和审慎性。

## 6. LLM Agent 的局限与评估

### 为什么会产生幻觉

LLM Agent 产生幻觉的原因包括：

- LLM 本质上是基于上下文预测下一个 token，并不天然等于事实数据库。
- 模型可能把训练语料中的模式迁移到当前问题，生成看似合理但实际错误的内容。
- 工具返回的信息可能不完整、过期或格式不清晰。
- Agent 可能错误理解 Observation，导致后续推理偏离事实。
- prompt 约束不足时，模型可能编造工具结果或过度推断。
- 上下文过长时，模型可能遗漏关键信息。

### 为什么需要最大循环次数

如果没有最大循环次数，Agent 可能陷入无限循环，例如：

- 反复调用同一个工具。
- 因格式错误不断重试。
- 得不到有效 Observation 却持续规划。
- 在多个备选方案之间来回摇摆。
- 无法判断任务已经完成。

这会导致 token 成本、API 调用成本和执行时间不断增加，也可能造成外部系统的重复操作风险。

### 如何评估智能体的智能程度

不能只用准确率评估智能体。准确率只能衡量最终答案是否正确，但 Agent 的价值体现在完整任务执行过程。

更全面的指标包括：

- 任务完成率。
- 工具调用正确率。
- 规划步骤是否合理。
- 完成任务所需轮数。
- 错误恢复能力。
- 幻觉率。
- 成本和延迟。
- 安全性和权限控制。
- 可解释性。
- 用户满意度。

对于 Agent 来说，“智能”不是单轮问答答对，而是能否在复杂环境中稳定、低成本、可控地完成任务。
