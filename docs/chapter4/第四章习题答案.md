## 更完善的参考答案

### 1. ReAct、Plan-and-Solve、Reflection 的区别与组合

#### 1.1 三种范式在“思考”和“行动”组织方式上的本质区别

三者都包含循环，但循环的目标不同：

| 范式 | 组织方式 | 每轮核心问题 | 状态/反馈来源 |
| --- | --- | --- | --- |
| ReAct | 思考和行动交替进行 | 下一步该调用什么工具，或是否结束？ | 外部工具返回的 Observation |
| Plan-and-Solve | 先整体规划，再按步骤执行 | 当前计划步骤如何完成？ | 原始计划、已完成步骤和历史结果 |
| Reflection | 先生成，再审查，再优化 | 当前产物哪里不好，如何改进？ | 自评、评审模型、测试结果或外部评价 |

ReAct 的核心是“边做边看”，适合信息不完整、需要与环境交互的任务。Plan-and-Solve 的核心是“先拆再做”，适合结构清晰、目标可分解的任务。Reflection 的核心是“做完再改”，适合需要质量提升、风格优化、错误修正的任务。

#### 1.2 智能家居控制助手适合什么范式？

我会选择以 ReAct 为执行核心，再叠加 Plan-and-Solve 和 Reflection：

- ReAct 适合作为实时控制循环，因为智能家居助手需要查询设备状态、调用设备 API、读取传感器结果，并根据真实反馈调整下一步动作。
- Plan-and-Solve 适合处理复杂场景，例如“我晚上 10 点准备睡觉，帮我调整全屋环境”，这类任务需要拆成灯光、空调、窗帘、安防、闹钟等子步骤。
- Reflection 适合做策略审查，例如用户习惯是否被误判、是否存在安全风险、能耗是否异常、用户是否可能不满意。

因此基础架构可以是：

```text
用户意图
  -> Planner: 识别场景并生成控制计划
  -> ReAct Executor: 查询设备状态并调用设备工具
  -> Safety/Reflection Reviewer: 检查安全、舒适度、能耗和用户偏好
  -> 最终执行或请求用户确认
```

#### 1.3 是否可以组合使用？

可以，而且真实 Agent 系统通常就是组合范式。以旅行助手为例：

```text
Plan-and-Solve:
  先规划整体行程框架，例如航班、酒店、交通、景点、预算。

ReAct:
  每个子任务执行时调用外部工具，例如航班 API、酒店 API、天气查询、地图路线、景点开放时间。

Reflection:
  生成初版方案后，从预算、时间衔接、风险、用户偏好、备选方案等角度自评并优化。
```

这种组合适合长期、多步骤、依赖外部信息、且最终结果需要质量审查的任务，例如旅行规划、软件开发、投研分析、客服工单处理等。

### 2. ReAct 输出解析的脆弱性与更鲁棒方案

#### 2.1 当前正则解析的潜在问题

正则解析适合教学 demo，但在真实模型输出里比较脆弱。常见失败场景包括：

- 模型输出多个 `Action:`，解析器可能取错动作。
- 模型擅自输出 `Observation:`，导致工具输入被污染。
- 模型在 `Action:` 后追加解释文字，正则可能把解释也吞进去。
- 工具参数里本身包含 `]`、换行、代码块或 JSON，简单正则容易截断。
- 模型忘记输出 `Action:`，或者输出成中文“行动：”。
- 模型调用了不存在的工具名。
- 工具参数类型不符合预期，例如计算器需要表达式，模型却传入自然语言长句。

你之前跑 ReAct 时遇到的问题就是典型例子：模型输出了 `Observation` 和第二个 `Action: Finish[...]`，旧解析器把后续文本全部当成 Search query。

#### 2.2 更鲁棒的解析方案

更可靠的方案包括：

- 使用 JSON 输出格式，并用 `json.loads` + schema 校验解析。
- 使用模型厂商提供的 function calling / tool calling。
- 使用 Pydantic、JSON Schema 或 dataclass 做结构校验。
- 使用 parser retry：解析失败时，把错误反馈给模型，让它只修格式。
- 使用工具路由层：先判断工具名是否合法，再判断参数是否符合工具 schema。
- 对高风险动作增加 human confirmation，例如发邮件、支付、删除数据、控制设备。

#### 2.3 示例：用 JSON 替代自由文本 Action

提示词可以要求模型只输出 JSON：

```text
请严格输出 JSON，不要输出 Markdown，不要输出额外解释。

格式如下：
{
  "thought": "你的简短思考",
  "action": {
    "name": "Search 或 Calculator 或 Finish",
    "input": "工具输入或最终答案"
  }
}
```

解析代码示例：

```python
import json


VALID_TOOLS = {"Search", "Calculator", "Finish"}


def parse_agent_output(text: str) -> tuple[str | None, str | None, str | None]:
    """Parse a structured ReAct response.

    Returns:
        thought, action_name, action_input
    """
    try:
        data = json.loads(text)
    except json.JSONDecodeError:
        return None, None, "输出不是合法 JSON，请严格按 JSON 格式重试。"

    thought = data.get("thought")
    action = data.get("action")
    if not isinstance(action, dict):
        return thought, None, "action 必须是对象，包含 name 和 input。"

    action_name = action.get("name")
    action_input = action.get("input")

    if action_name not in VALID_TOOLS:
        return thought, None, f"未知工具: {action_name}。可用工具: {sorted(VALID_TOOLS)}"

    if not isinstance(action_input, str) or not action_input.strip():
        return thought, None, "action.input 必须是非空字符串。"

    return thought, action_name, action_input
```

两种方案对比：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 正则解析 | 简单、直观、适合教学 | 容易被多余文本、多个 Action、括号嵌套击穿 |
| JSON/schema 解析 | 结构明确、可校验、易扩展工具参数 | 提示词更严格，模型仍可能输出非法 JSON，需要 retry |
| 原生 tool calling | 最稳定，工具名和参数由 API 结构化返回 | 依赖具体模型 API，不如纯文本方案通用 |

### 3. 工具调用扩展实践

#### 3.1 添加计算器工具

不要直接使用 `eval` 执行模型传入的表达式，因为这会带来代码执行风险。更安全的方式是使用 `ast` 只允许数学表达式。

```python
import ast
import operator


OPERATORS = {
    ast.Add: operator.add,
    ast.Sub: operator.sub,
    ast.Mult: operator.mul,
    ast.Div: operator.truediv,
    ast.FloorDiv: operator.floordiv,
    ast.Mod: operator.mod,
    ast.Pow: operator.pow,
    ast.USub: operator.neg,
    ast.UAdd: operator.pos,
}


def _eval_math_node(node):
    if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
        return node.value

    if isinstance(node, ast.BinOp) and type(node.op) in OPERATORS:
        left = _eval_math_node(node.left)
        right = _eval_math_node(node.right)
        return OPERATORS[type(node.op)](left, right)

    if isinstance(node, ast.UnaryOp) and type(node.op) in OPERATORS:
        value = _eval_math_node(node.operand)
        return OPERATORS[type(node.op)](value)

    raise ValueError("只支持数字和基础数学运算。")


def calculator(expression: str) -> str:
    """Safely calculate a math expression."""
    try:
        normalized = expression.replace("×", "*").replace("÷", "/")
        tree = ast.parse(normalized, mode="eval")
        result = _eval_math_node(tree.body)
        return str(result)
    except Exception as exc:
        return f"计算失败: {exc}"
```

注册工具：

```python
calculator_desc = "安全计算数学表达式，只支持数字、括号和基础四则/幂运算。"
tool_executor.registerTool("Calculator", calculator_desc, calculator)
```

如果用户问：

```text
计算 (123 + 456) × 789 / 12 = ?
```

理想 Action 是：

```text
Action: Calculator[(123 + 456) * 789 / 12]
```

#### 3.2 工具选择失败的处理机制

可以设计一个“工具调用失败管理器”，记录失败次数，并把可操作的纠错信息反馈给模型。

核心机制：

- 执行前校验工具名是否存在。
- 执行前校验工具参数是否为空、是否符合 schema。
- 工具执行异常时，不直接中断，而是把错误作为 Observation 返回。
- 同一工具或同一类错误连续失败超过阈值后，强制模型重新选择工具或请求用户补充信息。
- 对高风险工具设置人工确认。

伪代码：

```python
failure_count = 0
max_failures = 3

tool = tool_executor.getTool(tool_name)
if not tool:
    failure_count += 1
    observation = (
        f"工具选择失败: {tool_name} 不存在。"
        f"可用工具包括: {tool_executor.getAvailableTools()}。"
        "请重新选择一个工具，并只输出一个 Action。"
    )
elif not tool_input.strip():
    failure_count += 1
    observation = "工具参数为空。请提供明确的工具输入。"
else:
    observation = tool(tool_input)
    if observation.startswith("错误") or observation.startswith("计算失败"):
        failure_count += 1
    else:
        failure_count = 0

if failure_count >= max_failures:
    observation = (
        "连续多次工具调用失败。请停止继续尝试，"
        "先总结失败原因，并向用户询问缺失信息或请求人工介入。"
    )
```

这类机制的关键不是“让模型随便重试”，而是让系统把失败变成结构化反馈，引导模型修正。

#### 3.3 工具数量增加到 50 或 100 个时如何优化？

如果把 100 个工具的 name 和 description 全塞进 prompt，会出现几个问题：

- prompt 变长，token 成本上升。
- 模型注意力被稀释，选错工具概率上升。
- 工具描述之间可能相似，模型难以区分。
- 权限、参数 schema、风险等级难以统一管理。

工程上可以这样优化：

1. 工具分层分类：例如搜索类、计算类、文件类、数据库类、通信类、支付类。
2. 先做工具检索：根据用户问题，从工具库里召回最相关的 3 到 8 个工具，再放进 ReAct prompt。
3. 增加工具 router：先让一个轻量模型或规则系统判断需要哪类工具。
4. 为每个工具定义 schema：明确参数类型、必填字段、示例和错误处理。
5. 做权限和风险分级：低风险工具可直接执行，高风险工具需要确认。
6. 使用 embedding 检索工具描述，而不是每次把全部工具塞进上下文。

示例架构：

```text
User Query
  -> Tool Router: 判断任务类型
  -> Tool Retriever: 召回少量候选工具
  -> ReAct Agent: 只在候选工具中选择
  -> Tool Validator: 校验工具名、参数、权限
  -> Tool Execution
```

### 4. Plan-and-Solve 的动态重规划与分层规划

#### 4.1 如何设计动态重规划机制？

静态计划的问题是：计划生成时假设所有步骤都可完成，但现实中可能出现 API 不可用、信息缺失、前置假设错误、用户目标变化等情况。

动态重规划可以这样设计：

```text
生成初始计划
  -> 执行当前步骤
  -> 评估结果是否满足预期
      -> 满足: 进入下一步
      -> 不满足: 判断是否局部修复
          -> 可局部修复: 插入 t3.1、t3.2 这类补丁步骤
          -> 不可局部修复: 固化已完成事实，重写后续计划
```

关键设计：

- 保留 immutable facts：已经验证过的事实不要推翻，例如已查到的航班价格、用户预算、订单状态。
- 只重写 future plan：尽量只更新未执行的步骤，降低上下文混乱。
- 增加 step evaluator：每个步骤结束后判断“是否完成、是否可信、是否需要补查”。
- 记录 replan reason：每次重规划都记录原因，方便调试。

#### 4.2 商务旅行任务适合 Plan-and-Solve 还是 ReAct？

“预订一次从北京到上海的商务旅行”更适合混合范式，其中 Plan-and-Solve 负责主流程，ReAct 负责每个步骤的外部交互。

原因：

- 任务天然可分解：航班、酒店、租车、日程、预算、发票。
- 每个子任务都依赖外部信息：航班余票、酒店价格、交通时间、天气。
- 可能需要比较多个方案：价格、时间、距离、取消政策。
- 最终执行有高风险动作：下单、支付、发邮件，需要确认。

所以更合理的结构是：

```text
Planner:
  1. 确认出行时间和预算
  2. 查询航班
  3. 查询酒店
  4. 查询租车或接送
  5. 生成候选方案
  6. 请求用户确认
  7. 执行预订

ReAct Executor:
  每一步调用航班、酒店、地图、日历、邮件等工具。
```

#### 4.3 分层规划系统

分层规划是先生成高层计划，再对每个高层步骤生成子计划。

示例：

```text
高层计划:
  A. 明确需求
  B. 查询候选资源
  C. 生成方案
  D. 用户确认
  E. 执行预订

子计划 B:
  B1. 查询航班
  B2. 查询酒店
  B3. 查询地面交通
  B4. 检查时间衔接
  B5. 汇总候选项
```

优势：

- 降低一次性计划过长导致的错误。
- 每层计划更清晰，便于调试和替换。
- 可以对重要步骤单独使用 ReAct 或 Reflection。
- 适合长任务，因为上下文可以按层级压缩。

### 5. Reflection 的模型分工、终止条件和论文助手设计

#### 5.1 使用强模型反思、弱模型执行的影响

可能收益：

- 强模型做 review，可以发现弱模型产物中的深层问题。
- 弱模型执行更快、更便宜，适合生成初稿或机械修改。
- 对代码、写作、规划等任务，可以把“判断能力”和“执行能力”拆开优化成本。

可能风险：

- 弱模型可能无法正确理解强模型反馈，导致多轮返工。
- 强模型 feedback 太抽象，弱模型执行不到位。
- 多模型风格不一致，输出可能来回震荡。
- 如果没有测试或评分器，强模型也可能给出看似合理但错误的建议。

更稳的做法是：

```text
弱模型生成初稿
  -> 强模型给结构化 critique
  -> 弱模型按 critique 修改
  -> 测试/规则/评分器验证
  -> 必要时强模型再次裁决
```

#### 5.2 更智能的终止条件

只检查“无需改进”不够可靠，因为模型可能过早自信，也可能一直提出无意义修改。

更好的终止条件可以组合多个信号：

- 达到最大迭代次数。
- 单元测试、lint、类型检查全部通过。
- 评分器分数超过阈值，例如质量分 >= 8/10。
- 最近两轮改动很小，diff 收敛。
- review 反馈只剩低优先级建议。
- token、时间或成本预算耗尽。
- 高风险任务进入人工确认。

示例：

```python
def should_stop(iteration, max_iterations, tests_passed, score, critical_issues, diff_size):
    if iteration >= max_iterations:
        return True
    if tests_passed and score >= 8 and critical_issues == 0:
        return True
    if tests_passed and critical_issues == 0 and diff_size < 20:
        return True
    return False
```

#### 5.3 学术论文写作助手的多维 Reflection 机制

可以把 Reflection 拆成多个 reviewer，每个 reviewer 只关注一个维度：

```text
Draft Writer:
  生成论文初稿

Logic Reviewer:
  检查段落结构、论证链条、结论是否由证据支持

Novelty Reviewer:
  检查方法创新性、与已有工作的差异、贡献表述是否清楚

Method Reviewer:
  检查实验设计、变量控制、指标选择、消融实验是否充分

Language Reviewer:
  检查语言表达、学术风格、术语一致性

Citation Reviewer:
  检查引用格式、引用是否支持对应论断、是否缺少关键相关工作

Refiner:
  汇总多维反馈，生成修订版
```

每轮可以输出结构化反馈：

```json
{
  "dimension": "method",
  "score": 7,
  "critical_issues": [
    "缺少与强基线方法的对比",
    "消融实验没有单独验证检索模块的贡献"
  ],
  "suggested_revision": "增加 baseline comparison 和 ablation study 描述。"
}
```

这种设计比单一“请优化论文”更稳定，因为每个反思维度都有明确评价标准。

### 6. 提示词工程分析

#### 6.1 ReAct prompt 与 Plan-and-Solve prompt 的结构差异

ReAct prompt 的重点是让模型每轮输出：

```text
Thought
Action
```

它必须强调可用工具、Action 格式、历史 Observation，因为 ReAct 的核心是“根据环境反馈决定下一步动作”。

Plan-and-Solve prompt 的重点是让模型先输出完整计划，或在执行阶段只解决当前步骤。它需要强调：

- 原始问题是什么。
- 完整计划是什么。
- 当前执行到哪一步。
- 历史步骤结果是什么。

所以两者提示词的差异服务于不同控制流：

| 维度 | ReAct | Plan-and-Solve |
| --- | --- | --- |
| 输出粒度 | 一轮一个动作 | 一次生成计划，之后逐步执行 |
| 上下文重点 | 工具列表、Observation 历史 | 原始问题、完整计划、步骤历史 |
| 风险 | 工具调用格式错、循环失控 | 初始计划错、后续步骤僵化 |
| prompt 目标 | 约束下一步动作 | 约束分解和逐步完成 |

#### 6.2 角色设定对 Reflection 的影响

如果把角色从：

```text
你是一位极其严格的代码评审专家和资深算法工程师
```

改成：

```text
你是一位注重代码可读性和长期维护成本的开源项目维护者
```

输出重点会明显变化：

- 原角色更关注时间复杂度、算法瓶颈、性能优化。
- 新角色更关注命名、注释、函数拆分、边界条件、可测试性、API 清晰度。

这说明角色设定不是装饰，它会改变模型的评价标准。Reflection 中的 reviewer 角色越具体，反馈越可执行。

#### 6.3 few-shot 示例

可以给 ReAct 增加一个 few-shot，帮助模型遵守格式：

```text
示例：

Question: 计算 (12 + 8) * 3
History:

Thought: 这是一个数学计算问题，应使用 Calculator 工具。
Action: Calculator[(12 + 8) * 3]

Observation: 60

Thought: 已经得到计算结果，可以结束。
Action: Finish[计算结果是 60。]

现在请回答真实问题。注意每轮只能输出一个 Thought 和一个 Action，不要输出 Observation。
```

few-shot 的作用：

- 降低格式错误概率。
- 让模型理解工具调用和最终回答的边界。
- 对小模型或指令遵循较弱的模型尤其有效。

缺点是会增加 prompt 长度，并可能让模型过度模仿示例内容，所以示例应短、典型、格式稳定。

### 7. 电商客服智能体系统设计

#### 7.1 选择什么范式？

我会使用混合范式：

```text
Plan-and-Solve:
  拆解客服任务流程。

ReAct:
  查询订单、物流、退款政策、用户历史记录，并调用邮件发送工具。

Reflection:
  对低置信度、争议退款、高金额订单、异常用户情绪进行自我审查。
```

核心流程：

```text
用户退款请求
  -> 意图识别和信息抽取
  -> 查询订单与物流
  -> 查询退款政策
  -> 生成初步决策
  -> 置信度评估
      -> 高置信度: 生成回复并执行
      -> 低置信度: Reflection 审查或转人工
  -> 发送邮件/站内信
  -> 记录工单日志
```

#### 7.2 至少 3 个工具

可以设计以下工具：

| 工具名 | 功能 |
| --- | --- |
| `OrderLookup` | 根据用户 ID 或订单号查询订单金额、商品、支付状态、购买时间 |
| `LogisticsLookup` | 查询物流状态、签收时间、异常派送信息 |
| `RefundPolicySearch` | 检索公司退款政策，例如可退期限、商品品类限制、特殊活动规则 |
| `UserHistoryLookup` | 查询用户历史退款次数、投诉记录、会员等级 |
| `RefundDecisionTool` | 根据结构化输入计算是否满足退款条件，并返回规则依据 |
| `EmailDraftTool` | 根据决策和语气要求生成邮件草稿 |
| `EmailSendTool` | 在用户确认或系统授权后发送邮件 |
| `HumanEscalationTool` | 将争议案例转给人工客服 |

#### 7.3 提示词如何兼顾公司利益和用户友好？

提示词应明确三类约束：事实、政策、语气。

示例：

```text
你是电商平台的客服智能体。你的目标是在遵守公司退款政策的前提下，尽可能提供友好、清晰、可执行的帮助。

决策原则：
1. 不得编造订单、物流或政策信息。
2. 必须基于工具返回的订单信息、物流状态和退款政策做判断。
3. 如果信息不足，必须先询问用户或转人工，不得擅自批准或拒绝。
4. 对用户保持礼貌、同理心和清晰解释。
5. 如果拒绝退款，必须说明具体政策依据，并提供可选的后续方案。
6. 高金额订单、规则冲突、用户强烈不满、置信度低于 0.75 时必须转人工复核。

输出格式：
- decision: approve / reject / need_more_info / escalate
- confidence: 0 到 1
- policy_basis: 使用到的政策依据
- customer_message: 给用户的回复草稿
- internal_note: 给客服团队看的内部备注
```

#### 7.4 风险与技术缓解方案

| 风险 | 说明 | 缓解方案 |
| --- | --- | --- |
| 错批退款 | 给不符合政策的订单退款 | 规则引擎校验、高金额人工确认 |
| 错拒退款 | 损害用户体验和合规风险 | 低置信度转人工、保留申诉入口 |
| 编造信息 | 模型幻觉订单状态或政策 | 所有事实必须来自工具，禁止无来源判断 |
| 用户隐私泄露 | 回复中暴露敏感信息 | PII 脱敏、权限控制、日志审计 |
| 语气不当 | 加剧投诉 | 邮件发送前做 tone review |
| 工具调用失败 | 订单或物流系统不可用 | 降级策略、重试、人工接管 |
| Prompt injection | 用户诱导模型绕过政策 | 系统提示优先级、工具权限隔离、输入过滤 |
| 决策不可解释 | 用户或监管无法理解 | 输出 policy_basis 和 internal_note |

最终产品不应让 LLM 单独决定退款，而应采用：

```text
LLM 理解和沟通
规则/工具负责事实与政策校验
Reflection 负责争议审查
人工负责高风险兜底
```

这才是客服智能体从 demo 走向生产系统时更稳妥的架构。
